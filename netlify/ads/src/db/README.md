# `db/` — database access + schema/migrations

Typed Postgres (Supabase) access via **Drizzle ORM**, plus versioned SQL migrations.

## Layout

- `schema/` — one file per table (`adAccounts`, `campaigns`, `adSets`, `ads`,
  `creatives`, `dailyAdInsights`, `syncRuns`, `manualCampaignContext`,
  `metricDefinitions`) + `columns.ts` (shared audit/presence column builders) +
  `index.ts` (barrel).
- `migrations/` — SQL generated by `npm run db:generate` (never hand-edited).
- `reconciliation.ts` — pure presence/soft-delete state rules (no DB/network).
- `seed.ts` — idempotent `metric_definitions` seed (upsert on `key`).

## Key rules baked into the schema

- **UUID** primary keys; **Meta IDs are `text`** and globally unique.
- **`daily_ad_insights`** = one row per `(ad, date)`; `UNIQUE(ad_id, date)` makes
  re-syncs upsert, never duplicate. Parent ids are denormalised for fast filters.
- **Money units:** `spend` is stored in **major** units (Meta returns a decimal);
  ad-set budgets are stored as **`_minor` bigint** (Meta returns int64 minor
  units, e.g. pence) — major value is derived at read time, never assumed.
- **Reported vs calculated:** Meta's own daily ratios/costs are `reported_*` and
  are provenance ONLY; the metrics layer recomputes period figures from summed
  base columns.
- **Deletion:** never hard-delete. `last_seen_at` / `missing_since` /
  `consecutive_full_scope_misses` / `deleted_at` track presence; `deleted_at` is
  set only by an explicit Meta signal or a future reviewed rule — never by
  absence. See `reconciliation.ts`.
- **Unverified fields** (e.g. `video_thruplay_watched_actions`, creative identity
  refs) get no typed column yet — they live in `raw_snapshot` / JSONB until
  verified, then arrive via a reviewed migration.

## Ingestion / write layer (Stage 6)

- `client.ts` — the runtime, **server-only** pooled connection (`DATABASE_URL`,
  Supavisor TRANSACTION mode 6543, `prepare: false`). The single module allowed to
  import the `postgres` driver; never browser-reachable. Stage 6 is offline-only
  (PGlite-tested) — this performs no live write yet.
- `ingest/` — idempotent upsert writers + Meta-ID → UUID resolution: `index.ts`
  (orchestrator), `upsertDimensions.ts`, `upsertInsights.ts`, `resolveIds.ts`,
  `windows.ts` (deterministic 7-day windows), `dbErrors.ts` (classification,
  bounded retry, error sanitisation).
- `syncRuns.ts` — `sync_runs` lifecycle (created/updated OUTSIDE data
  transactions).
- The future fetch-and-write workflow (`src/sync/`) will orchestrate these.
- **Bigint:** 15 count/budget columns use `mode: 'bigint'` (Stage 6) — lossless
  across the write boundary, no DDL change. See `docs/STAGE-6-INGESTION.md`.

## Connections & scripts (Stage 3)

There is a runtime `src/db/client.ts` (Stage 6, above) but the application still
has no live queries wired up. Live operational work is done by **script-only**
helpers under `scripts/db/`, which read `MIGRATION_DATABASE_URL` and must never be
imported by browser/application code.

**Connection modes (Supavisor, IPv4 — the direct IPv6-only connection is unused):**

- **Migrations / scripts → Supavisor SESSION mode, port 5432.** Supports the
  session features migrations rely on. Used by `scripts/db/*`.
- **Runtime (future) → Supavisor TRANSACTION mode, port 6543** with
  `postgres.js` `prepare: false`. Added at the server/API stage in
  `src/db/client.ts`.

**Roles:** migrations run as the Supabase **owner** connection. A restricted
runtime role, its grants, and any RLS **policies** are deferred to the server/API
stage (no `BYPASSRLS` runtime role, no broad owner-level runtime access).

**Scripts (run manually in Gate 2 only).** Nothing auto-loads an env file — the
scripts read `MIGRATION_DATABASE_URL` from the process environment ONLY. Provide
it for the current terminal session (never echo it, paste it into chat, commit
it, or leave it in shell history where avoidable):

```sh
export MIGRATION_DATABASE_URL='<Supavisor session-mode connection string>'
```

| Command                  | Does                                                                    |
| ------------------------ | ----------------------------------------------------------------------- |
| `npm run db:ping`        | `select 1` connection check                                             |
| `npm run db:migrate`     | snapshot → apply migrations once → inspect                              |
| `npm run db:verify`      | assert 9 tables + RLS-on-all + no policies + migration metadata         |
| `npm run db:seed`        | seed `metric_definitions` and prove idempotency (before/after counts)   |
| `npm run db:verify-anon` | assert the anon role can read ZERO rows from all 9 tables via PostgREST |

Run them in order: `db:ping` → `db:migrate` → `db:verify` → `db:seed` →
`db:verify-anon`. When Gate 2 is complete, clear the variable (it only affects
the current session):

```sh
unset MIGRATION_DATABASE_URL
```

**`db:verify-anon` needs two extra variables.** Unlike the other scripts (which
use only `MIGRATION_DATABASE_URL`), the anon read check calls PostgREST and so
temporarily requires `SUPABASE_URL` and `SUPABASE_ANON_KEY`:

```sh
export SUPABASE_URL='https://<project-ref>.supabase.co'
export SUPABASE_ANON_KEY='<publishable/anon key>'
npm run db:verify-anon
```

These two are:

- used **only** for the one-off live RLS / PostgREST verification in Gate 2;
- exported **only** in the current terminal session (never echoed, pasted into
  chat, committed, or left in shell history where avoidable);
- **not** added to `.env.example` yet — they land there in a later stage (see the
  Future environment variables table below);
- **unset immediately** after the check:

```sh
unset SUPABASE_URL SUPABASE_ANON_KEY
```

`db:generate` remains offline (no connection).

### Migration failure & recovery (runbook)

Drizzle's `postgres-js` migrator is **not assumed atomic** — verify actual
behaviour before relying on it. On any error: **stop**, do not edit migration
bookkeeping, do not mark a failed migration complete, do not re-run blindly, and
never hand-edit the committed `0000` migration. If the schema partially changed,
record exactly what changed and propose a reviewed forward-fix (or, during
initial setup only, drop/recreate the empty project). All script output is
redacted — connection strings, passwords, hosts, usernames and keys are never
logged.

## Automated tests

Run entirely on **PGlite** (in-memory Postgres) — no credentials, no network:
schema/constraints/upsert/reconciliation/seed (Stage 2), plus RLS-enabled +
no-policies, connection-string validation/redaction, and server-only import
boundaries (Stage 3). Live-DB checks (apply, verify, seed idempotency, anon
cannot read via PostREST) are gated to Gate 2 against the real project.

## Stage 9 — runtime preflight and rollback

See **`docs/STAGE-9-RUNBOOK.md`** for the full ordered procedure.

### `npm run db:preflight` (read-only)

Exercises `DATABASE_URL` — Supavisor **TRANSACTION** mode (6543), `prepare:
false` — which had **never opened a socket** before Stage 9: Stage 3 used
`MIGRATION_DATABASE_URL` (session mode, 5432), and Stages 6–8 used PGlite. It
reports the redacted target, connectivity, SELECT/INSERT/UPDATE privileges and
RLS compatibility on the seven write-path tables, both timeouts, and row counts.

**RLS is the point.** Every table has RLS enabled with **zero policies**
(default-deny), so the write role must own the tables (un-FORCEd) or hold
`BYPASSRLS`, or writes are silently filtered to nothing. `writePathUsable: false`
blocks the run.

Writes nothing: `select` only, inside `SET TRANSACTION READ ONLY`, with a
boundary test scanning for write verbs.

### `npm run db:rollback-stage9` (deletes data)

The only script that deletes application data, scoped to **one** Meta ad account
and not widenable. Gates (all fail closed): `DB_CONFIRM_ROLLBACK=1`,
`--confirm-rollback`, `--account act_<id>`, `MIGRATION_DATABASE_URL`.

Deletes in FK-safe order in one transaction: `daily_ad_insights` → `ads` →
`creatives` → `ad_sets` → `campaigns` → `ad_accounts`.

Two behaviours worth knowing, both driven by the schema's FKs:

- **`sync_runs` rows are preserved, but their `ad_account_id` is cleared.** That
  FK is `ON DELETE RESTRICT`, so a populated run row pins its account against
  deletion. Every column carrying evidence survives; only the pointer to a
  now-deleted account goes.
- **It refuses if `manual_campaign_context` exists for the account's campaigns.**
  That is the schema's one `ON DELETE CASCADE`, so a campaign delete would
  silently destroy human-authored text. It stops rather than be quietly
  destructive.
